# Neural Machine Translation System (English to Hindi)

An end-to-end Neural Machine Translation (NMT) Application that automatically translates English sentences into Hindi using an Encoder–Decoder architecture. Developed for Assignment 2 (GS-1).

---

## Project Overview
* **Application Domain:** Digital content localization and educational accessibility.
* **Target Users:** Non-English native speakers requiring access to regional language content.
* **Language Pair:** English (`en`) → Hindi (`hi`)
* **Dataset:** [AI4Bharat Samanantar Corpus](https://huggingface.co/datasets/ai4bharat/samanantar) (CC BY-NC 4.0 — non-commercial use; verify current terms on the dataset card before submission)
* **Dataset Size:** 48,724 cleaned sentence pairs (5–30 token length constraint applied on the English side)
* **Data Split:** 80% Train (38,979) / 10% Validation (4,872) / 10% Test (4,873)
* **Fixed Sequence Length (`MAX_LEN`):** 34 (including `<sos>` and `<eos>`)
* **Vocabulary Sizes:** English: **12,370** tokens | Hindi: **11,354** tokens (built with `min_freq=4` — see "Design decisions" for why this was tuned down from an earlier `min_freq=2` run that gave 23,553/21,233 tokens)

## Setup Instructions

### 1. Requirements
* **Python 3.10+** (developed and tested on Python 3.11; PyTorch 2.2+ requires Python ≥3.9)
* A CUDA-capable GPU is strongly recommended for training (training for this submission was run on GPU; CPU training will take considerably longer — see "Known issues"). The Streamlit app itself runs fine on CPU once a checkpoint exists.
* ~2 GB free disk space for the raw dataset cache, plus space for a trained checkpoint

### 2. Create a virtual environment
```bash
python -m venv venv
```
Windows PowerShell:
```powershell
venv\Scripts\Activate.ps1
```
macOS/Linux:
```bash
source venv/bin/activate
```

### 3. Install dependencies
```bash
pip install -r requirements.txt
```

### 4. Set up the data and model files
This repo's `data/` folder already contains the **preprocessed** artifacts needed to train, evaluate, or run the app (`src_vocab.json`, `tgt_vocab.json`, `train_ids.json`, `val_ids.json`, `test_ids.json`, `config.json`) — no download needed for these.

What you additionally need, depending on what you want to do:
* **To run the app / run inference / run evaluation:** you need a trained checkpoint at `models/nmt_model.pt`.
  * This file is **not included in the submitted ZIP** because of its size (see "Known issues"). Train it yourself with the command in step 5 below.
  * Place the resulting checkpoint at `./models/nmt_model.pt` — this is exactly where `train.py` writes it, so no manual step is needed if you train locally.
* **To regenerate the data from scratch** (not required for grading — the processed files are already in `data/`): run `python run_pipeline.py --min_freq 4`. This re-downloads the Samanantar corpus from Hugging Face (`datasets` library, streaming mode) and requires internet access.

### 5. Train the model
```bash
python train.py
```
This uses the script's current defaults: `emb_dim=128, hid_dim=256, dropout=0.4, weight_decay=1e-4, lr=1e-3, teacher_forcing_ratio=0.6, label_smoothing=0.1, patience=4, epochs=15`. Outputs are written to `./models/`: `nmt_model.pt`, `loss_curve.png`, `training_log.json`.

Key optional flags: `--lr`, `--dropout`, `--hid_dim`, `--emb_dim`, `--clip` (gradient clipping), `--teacher_forcing_ratio`, `--label_smoothing`, `--patience`.

**To continue training an existing checkpoint** (e.g. if it's still improving and hasn't early-stopped), use `--resume`:
```bash
python train.py --resume --epochs 60 --lr 5e-4 --patience 6
```
This loads `models/nmt_model.pt`, picks up counting epochs from where it left off, and optionally applies a lower learning rate to help push past a plateau. The model used for this submission was trained in two phases this way: 15 epochs from scratch, then resumed to epoch 25 (best checkpoint) with a lower LR before early stopping confirmed a genuine plateau — see "Design decisions" below.

**Note on training time:** even with the smaller architecture, LSTM training on ~39k pairs took roughly 70–190s/epoch on GPU in our runs; CPU training will be substantially slower (LSTMs are sequential). Use a GPU runtime (e.g. the BITS OSHA Virtual Lab GPU option, if available, or Colab) for a full run, or use `--epochs 2` for a quick smoke-test.

## Application Development (Task 4)

### Running the application
Once `models/nmt_model.pt` exists (see Setup step 4–5), and the vocabulary files are in place at:
```text
models/nmt_model.pt
data/src_vocab.json
data/tgt_vocab.json
```
start the app with:
```bash
streamlit run app.py
```
The application will be available locally at:
```text
http://localhost:8501
```

### Application features
1. **Single-sentence translation** — enter English text and view the generated Hindi translation.
2. **Greedy decoding** — generates a translation using greedy decoding.
3. **Beam-search decoding** — beam-search decoding with a configurable beam width (recommended over greedy — see "Design decisions").
4. **Batch translation** — upload a `.txt` file (one English sentence per line) or a `.csv` file (with an `english` column).
5. **Original and translated text display** — shows the English input alongside the generated Hindi translation.
6. **CSV output** — batch translation results can be downloaded as a CSV file.

### Batch input format
For a `.txt` file, one English sentence per line:
```text
How are you today?
This is a very important meeting.
The government announced a new policy for farmers.
```
For a `.csv` file, include an `english` column:
```csv
english
How are you today?
This is a very important meeting.
The government announced a new policy for farmers.
```

### CLI inference (optional, no Streamlit needed)
```bash
python infer.py "how are you today"
python infer.py "how are you today" --decoding beam --beam_width 5
python infer.py --file test_input.txt --output results.csv
```

## Model Architecture & Training (Task 3)
* **Architecture:** Bidirectional LSTM Encoder + LSTM Decoder with **Bahdanau (additive) attention**, separate source/target embeddings (`emb_dim=128`, `hid_dim=256`).
* **Encoder:** Single-layer BiLSTM; final forward/backward states are projected (`Linear + tanh`) into the decoder's initial hidden/cell state.
* **Decoder:** LSTM that at each step attends over all encoder outputs, concatenates the resulting context vector with the token embedding, and predicts the next target token.
* **Loss:** Token-level cross-entropy with label smoothing (0.1), ignoring `<pad>` positions.
* **Regularization:** dropout 0.4, weight decay 1e-4, gradient clipping (max norm 1.0), `ReduceLROnPlateau` LR scheduling (factor 0.5, patience 2), early stopping (patience 4–6 depending on run).
* **Decoding:** Both **greedy decoding** and **beam search** (configurable beam width, length-normalized scoring) are implemented, plus a repetition-blocking constraint applied at decode time (see below).
* **Final checkpoint used for this submission:** epoch 25, validation loss 6.0097 (best of a resumed run; early stopping confirmed via four LR reductions — 1e-3 → 6.25e-5 — that this was a genuine plateau, not merely a learning-rate issue).

## Design decisions (and why they changed mid-project)

**1. Vocabulary size (`min_freq`).** An initial run used `min_freq=2`, giving a 23,553/21,233-word vocabulary. This was too large relative to the ~39k-sentence training set: the decoder's final output layer alone had ~38M parameters, and the model overfit almost immediately (validation loss stopped improving after epoch 3 while training loss kept dropping). We raised `min_freq` to 4 (12,370/11,354-word vocabulary) and shrank the model (`hid_dim` 512→256, `emb_dim` 256→128), which fixed the overfitting: validation loss improved steadily through epoch 25 instead of diverging after epoch 3.

**2. Repetition blocking at decode time.** Even after fixing the overfitting, greedy/beam decoding produced repeated-word loops (e.g. a word generated twice in a row) on some inputs — a known failure mode for LSTM-based Seq2Seq models trained on limited data, where the decoder's own previous output token strongly biases its next prediction. We added a **no-repeat constraint** at decode time (blocks the model from repeating the immediately preceding token, plus a general no-repeat-trigram rule) in `greedy_decode`/`beam_search_decode` in `train.py`. This is a standard decoding-time technique (comparable to Hugging Face's `no_repeat_ngram_size` argument in `generate()`) — **it constrains what the model is allowed to output, it does not improve the model's underlying quality.** On short/simple test sentences this fully eliminated visible repetition; on longer, multi-clause sentences it can reduce but not fully eliminate repetition (e.g. a two-word cycle may still appear) — this is disclosed as an observed limitation in the Evaluation section (Task 5) rather than hidden.

## Known Limitations
The application uses the trained NMT checkpoint generated during Task 3. Translation quality varies, particularly for longer sentences, rare or unseen words, named entities, and sentence structures underrepresented in the training data. The model may occasionally generate `<unk>` tokens or repeated words/phrases (partially mitigated by decode-time repetition blocking — see "Design decisions" — but not fully eliminated on longer/complex sentences). These limitations are discussed explicitly in the evaluation report (Task 5) rather than concealed.

## Known Issues
* **`models/nmt_model.pt` is not included in this submission's ZIP** — the checkpoint exceeds a practical size for the assignment upload. Retrain locally with the command in Setup step 5 (`python train.py`, optionally `--resume` to continue an existing checkpoint). `.gitattributes` tracks `models/*.pt` via Git LFS if this repo is cloned from Git instead.
* **The model has a genuine quality ceiling for this architecture/data size.** After fixing the overfitting (see "Design decisions"), validation loss plateaued around 6.0 despite four learning-rate reductions (1e-3 → 6.25e-5) across an extended resumed run — this rules out learning rate as the bottleneck and points to a real capacity/data-size limitation of a ~256-hidden-unit LSTM trained on ~39k sentence pairs.
* Regenerating data via `run_pipeline.py` requires internet access to Hugging Face (`datasets.load_dataset("ai4bharat/samanantar", ...)`).
* Training on CPU is slow; a GPU is recommended (see Setup step 5).
